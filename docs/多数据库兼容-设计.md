# 多数据库兼容：设计与改造计划

> 状态：阶段 1 已实现并在 PostgreSQL 16 / MySQL 8.0 / SQL Server 2019 上测试；阶段 2（跨库数据迁移）未实现。实现与验证结果见 `docs/多数据库部署与迁移指南.md`（只记录在真实容器上测过的内容）。

## 1. 目标与范围

| 引擎 | 目标版本 | 策略 |
|---|---|---|
| PostgreSQL | 14+（测试 16） | 现有部署保持原样（pgx 原生连接池，迁移文件与校验和不变） |
| MySQL | 8.0+（测试 8.0 与 8.4） | `database/sql` + `go-sql-driver/mysql`，InnoDB，utf8mb4 |
| SQL Server | 2019+（测试 2019、2022） | `database/sql` + `microsoft/go-mssqldb`，NVARCHAR |
| SQLite | 不支持 | Windows 独立安装继续用内嵌 PostgreSQL；SQLite 缺 `SKIP LOCKED`、并发写模型不同，不属于低成本、可完整测试的范围，故明确不做 |

## 2. 勘察结果：PostgreSQL 专有构造清单

SQL 全部集中在 `internal/store`（约 3000 行）、`internal/diag/store.go`、`internal/pipeline/service.go`（1 条）、`internal/api/diag.go`（3 条）和 `internal/db`（迁移）。业务层（api、pipeline、auth、storage、fileops）不直接写 SQL，通过 `store.Store`。

| 构造 | 位置 | 处理 |
|---|---|---|
| pgx 类型（`pgx.Row/Rows/Tx`、`pgconn.CommandTag`、`pgx.ErrNoRows`、`pgconn.PgError`） | store、diag、db、supervisor | 引入 `internal/sqldb` 的 `Row/Rows/Tx/CommandTag/ErrNoRows`，pgx 与 database/sql 各一个后端实现同一接口 |
| `$n` 占位符 | 全部（约 200 处） | 保持 `$n` 为“规范写法”，由 `sqldb` 翻译器按方言改写：MySQL `?`（按出现顺序重排/复制参数），MSSQL `@pN` |
| `::uuid/::text/::date/::timestamptz` | store 70+ 处 | 翻译器对 MySQL/MSSQL 去掉类型转换（ID 列是 CHAR(36)/NVARCHAR(36)，日期列是 DATE） |
| `now()` | store | 翻译为 `UTC_TIMESTAMP(6)` / `SYSUTCDATETIME()` |
| `gen_random_uuid()` | `EnqueueMissing` | `UUID()` / `LOWER(CONVERT(CHAR(36),NEWID()))` |
| `RETURNING`（18 处） | store/auth/config/ai/storage | 业务代码改成“事务内先写后按主键读回”（所有方言同一写法），不再依赖 `RETURNING`/`OUTPUT` |
| `ON CONFLICT (..) DO UPDATE / DO NOTHING` | store(config/ai/plans/storage)、diag | 翻译器：MySQL `ON DUPLICATE KEY UPDATE`，MSSQL `MERGE ... HOLDLOCK`；`diag` 的复杂 upsert（引用 `EXCLUDED`、`GREATEST`）改成可移植的“先 UPDATE，0 行再 INSERT，唯一冲突重试” |
| `ILIKE` | 文件/台账搜索 | 翻译为 `LOWER(col) LIKE LOWER(?) ESCAPE '!'`（三种方言行为一致：忽略大小写、不折叠重音；转义字符统一为 `!`） |
| `jsonb`、`->`、`jsonb_typeof` | 迁移、`analysis->'ocr'` | 列：PG jsonb / MySQL JSON / MSSQL NVARCHAR(MAX)+`ISJSON` CHECK；`->'ocr'` 改为读取整列后在 Go 中解析 |
| `TEXT[]`（`origins`、`transports`） | auth_settings、webauthn_credentials | PG 保持数组；MySQL/MSSQL 存 JSON 数组。通过方言提供的 `StringsArg/ScanStrings` 读写 |
| `BYTEA` | api_key_enc、webauthn、recovery_codes | MySQL `VARBINARY/LONGBLOB`，MSSQL `VARBINARY(MAX)`；JSON 参数一律以 `string` 传（避免二进制字符集写入 JSON 列/NVARCHAR 被按 UTF-16 误读） |
| `BIGSERIAL`（`error_occurrences.id`） | 009 | MySQL `BIGINT AUTO_INCREMENT`，MSSQL `BIGINT IDENTITY` |
| `TIMESTAMPTZ` | 全部 | 统一“只存 UTC”：MySQL `DATETIME(6)`、MSSQL `DATETIME2(6)`；写入时 `time.Time` 一律转 UTC；DSN 固定 `loc=UTC`、`time_zone='+00:00'` |
| `BOOLEAN` 裸谓词（`WHERE enabled`、`NOT cancel_requested`、`SELECT a OR b`） | store | 改成 `col=true`/`CASE`（MSSQL 无布尔类型）；翻译器把 `true/false` 字面量在 MSSQL 换成 `1/0` |
| `LIMIT n OFFSET m` | 全部分页 | 翻译器：MSSQL 使用 `OFFSET m ROWS FETCH NEXT n ROWS ONLY`（无 ORDER BY 时补 `ORDER BY (SELECT NULL)`），`LIMIT 1` 子查询改 `TOP (1)` |
| `FOR UPDATE [OF r] [SKIP LOCKED]`（持久队列 `ClaimJob`、`ClaimReplication`；`getPlan(lock)` 等 10 处） | store | MySQL 8.0+ 原生支持 `FOR UPDATE SKIP LOCKED`；MSSQL 翻译为表提示 `WITH (UPDLOCK, ROWLOCK[, READPAST])`。队列领取改成“事务内锁定选出 id → UPDATE → 读回” |
| `pg_advisory_xact_lock(hashtext())`（导入幂等键、迁移互斥） | store.Save、db.Migrate | 方言 `LockKey`：PG advisory xact lock；MSSQL `sp_getapplock`（事务范围）；MySQL `GET_LOCK`（事务结束时释放） |
| `ANY($1)` / `= ANY($1::uuid[])` | ledgerfs（3 处） | 展开为 `IN ($a,$b,…)`（分批） |
| `to_char(date,'YYYY-MM-DD')` | plans、store | 翻译为 `DATE_FORMAT` / `CONVERT(char(10),x,23)` |
| `lower(col)` 唯一索引 | storage_connections.name、users.username | MySQL 函数索引 `((lower(col)))`，MSSQL 持久化计算列 + 唯一索引；列使用二进制排序规则以保持 PG 的“大小写不敏感唯一、重音敏感”语义 |
| `||` 字符串连接、`substr`、`left`、`position(x in y)`、`starts_with`、`GREATEST`、`count(*) FILTER`、`interval '7 days'`、`GROUP BY 1,2` | store/diag/api | 改成可移植写法（`concat()`、`substr(x,n,len)`、LIKE、`CASE`、Go 里算时间） |
| 部分唯一索引 `WHERE x IS NOT NULL` | 002/003 | MySQL 唯一索引允许多个 NULL（直接建普通唯一索引）；MSSQL 过滤唯一索引 |
| 窗口函数 `row_number() OVER` | diag.Retention | MySQL 8 / MSSQL 均支持，保持 |
| `LISTEN/NOTIFY`、全文检索、`generate_series`、`COPY` | **未使用** | 无需处理（grep 命中的 `LISTEN` 为注释/日志文本） |
| `search_path`（测试隔离、schema 隔离） | dbtest | PG 用 `search_path`；MySQL 用独立 database；MSSQL 用独立 schema |
| `pgconn.PgError` 23505（唯一冲突） | store/auth | 方言 `IsUniqueViolation`（PG 23505，MySQL 1062，MSSQL 2627/2601） |
| 嵌入式 PostgreSQL | `internal/supervisor` | 仅 Windows 独立安装且未配置外部库时启动；配置了外部库则不启动 |

## 3. 架构改动（最小）

1. 新包 `internal/sqldb`：`Provider`、`Config`（含 TLS）、`Dialect`、`DB`（`Exec/Query/QueryRow/Begin/Ping/Close`）、SQL 翻译器、错误分类（唯一冲突/死锁/序列化失败/连接断开）、`InTx`（panic 与错误时回滚，仅对已分类的瞬时错误重试）、DSN 脱敏。PG 仍走 pgxpool 原生后端，其余走 `database/sql`。
2. `store.Store.Pool` 的类型从 `*pgxpool.Pool` 换为 `*sqldb.DB`，方法集合保持（`Exec/Query/QueryRow/Begin`），因此调用点基本是机械替换；SQL 仍只出现在 store/diag（“规范 PG 风格子集 + 翻译器”）。业务层无方言分支。
3. `internal/db`：迁移改为按方言目录：`migrations/*.sql`（PostgreSQL，保持不动，校验和不变）、`migrations/mysql/`、`migrations/mssql/`。迁移表 `schema_migrations(version, checksum, applied_at[, state])`；MySQL（DDL 自动提交）以步骤标记表 `schema_migration_steps` 实现幂等续跑与 dirty 检测；PG/MSSQL 使用事务 DDL，整个迁移要么全成功要么回滚。互斥：PG `pg_advisory_xact_lock`、MSSQL `sp_getapplock`、MySQL `GET_LOCK`。只执行 `*.up.sql`；`*.down.sql` 永不自动执行；迁移文件含 `-- oa:destructive` 标记时需要显式 `--allow-destructive`。
4. 新包 `internal/dbconfig`：配置来源（环境变量 > 数据目录 `database.json` > 内嵌 PG），密码与客户端私钥用 `internal/secrets`（AES-GCM）加密落盘，API/日志/诊断包不返回；`pending` 配置只在重启时、校验通过且管理员批准、目标库已初始化、并且不会把有数据的安装指向空库时才生效。
5. 隔离校验（`internal/db/isolation.go`）：按引擎检查专用库/schema、权限与“外来表”，拒绝无法保证隔离的目标，过度授权仅告警。
6. 管理员 API（`/v1/admin/database*`）+ 审计 + 前端设置页组件 `DatabaseSettings.vue`。
7. 初始化需要显式批准：先 dry-run 预览将执行的 DDL，返回绑定 DDL 哈希与目标配置的确认令牌，再带令牌执行。
8. 阶段 2：`internal/dbmigrate` + `cmd/oa-dbmigrate` + API/向导，见 §6。

## 4. 数据类型映射

| PG | MySQL 8 | SQL Server |
|---|---|---|
| UUID | CHAR(36) | CHAR(36) |
| TEXT（非索引） | LONGTEXT | NVARCHAR(MAX) |
| TEXT（主键/唯一/索引） | VARCHAR(n) utf8mb4（utf8mb4_bin 按需） | NVARCHAR(n≤450) |
| JSONB | JSON | NVARCHAR(MAX) + `CHECK (ISJSON(x)=1)` |
| TIMESTAMPTZ | DATETIME(6)（UTC） | DATETIME2(6)（UTC） |
| BOOLEAN | TINYINT(1) | BIT |
| BYTEA | LONGBLOB / VARBINARY(n) | VARBINARY(MAX) / VARBINARY(n) |
| TEXT[] | JSON | NVARCHAR(MAX)（JSON 数组） |
| BIGSERIAL | BIGINT AUTO_INCREMENT | BIGINT IDENTITY |

## 5. 阶段 1 验收（概要）

实测矩阵：postgres:16、mysql:8.0、mysql:8.4、mssql 2019-latest、2022-latest（受内存影响，逐个运行）。同一套 Go 集成测试通过 `OA_TEST_DATABASE_URL` / `OA_TEST_MYSQL_URL` / `OA_TEST_MSSQL_URL` 选择引擎，每个测试使用独立 schema/database。`scripts/test-db-matrix.sh|.ps1` 启停容器并逐引擎跑测试；`.github/workflows/db-matrix.yml` 在 CI 里用 service container 运行。

## 6. 阶段 2：跨库数据迁移（概要）

`internal/dbmigrate`：源/目标连通与版本校验 → 目标必须已初始化、同版本且为空（v1 拒绝合并）→ 源逻辑导出（带校验和）→ 预览（表、行数、预估耗时、警告）→ 按 FK 顺序、主键 keyset 分批、目标端每批一个事务、可续跑的进度文件 → 重置自增/identity → 校验（行数、外键完整性、关键列校验和、台账顺序、抽样深比较）→ 切换窗口使用维护模式（API 对写请求返回 503，队列暂停，失败时释放）→ 仅写入 `pending` 配置（重启生效，不自动切换）。源库只读，不删除任何数据；文件与预览缓存不复制，只核对引用路径是否存在。
