# 构建与发布

本文说明所有构建/打包脚本、前置条件、产物、签名、版本与发布清单、CI 用法。Windows 版是**单用户桌面版**（Electron 外壳 + 后端 `local` 模式，免登录）；Linux 版（Docker Compose，企业登录）由 `deploy/linux` 构建。

## 前置条件
| 工具 | 版本 | 说明 |
|---|---|---|
| Go | 1.26（见 `backend/go.mod`） | 构建后端 |
| Node.js | 22+（本机验证 24） | 前端、Electron、electron-builder |
| Python | 3.12 | 文档 Worker；需要虚拟环境 `workers\document-ai\.venv` |
| PyInstaller | 随 venv 安装 | `python -m venv workers\document-ai\.venv` 后 `workers\document-ai\.venv\Scripts\pip install -r workers\document-ai\requirements.txt pyinstaller` |
| PowerShell | Windows PowerShell 5.1 即可 | 脚本均为 UTF-8 **带 BOM** |
| 网络 | 首次需下载 Electron、NSIS、内置 PostgreSQL（Maven 中央库） | 下载缓存：`dist\cache`、`%LOCALAPPDATA%\electron`、`%LOCALAPPDATA%\electron-builder\Cache` |

国内网络可使用镜像：
```powershell
$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
$env:ELECTRON_BUILDER_BINARIES_MIRROR = "https://npmmirror.com/mirrors/electron-builder-binaries/"
$env:npm_config_registry = "https://registry.npmmirror.com"
```

## 脚本一览
所有 PowerShell 脚本：`powershell -ExecutionPolicy Bypass -File scripts\<name>.ps1 [参数]`，失败即停（非 0 退出码），每步有 `==>` 横幅，可重复运行（幂等），不含任何密钥。

| 脚本 | 作用 | 主要参数 | 输出 |
|---|---|---|---|
| `scripts\version.ps1` / `version.sh` | 解析版本：`-Version` > `$env:OA_VERSION` > 根目录 `VERSION` 文件 > `git describe`；导出 `OA_VERSION`/`OA_COMMIT` | `-Version` `-Quiet` | 环境变量与打印 |
| `scripts\build-backend.ps1` / `.sh` | 编译后端（`-Mode debug\|release`，`-trimpath`，ldflags 写入版本/commit；`-Arch x64\|arm64` 交叉编译 Windows 后端） | `-Mode` `-Out` `-Arch` | `backend\bin\oa-agent[-debug].exe` |
| `scripts\build-frontend.ps1` / `.sh` | `npm ci` + `npm run build` | `-Clean` `-SkipInstall` | `frontend\dist` |
| `scripts\build-worker.ps1` | PyInstaller onedir 构建文档 Worker（**始终 x64**：要求 x64 Python，否则报错） | `-Clean` | `dist\worker-dist\document-worker` |
| `scripts\build-server-bundle.ps1` | 后端 + 前端 + Worker + 内置 PostgreSQL（精简）+ 迁移 → 服务端包 | `-Mode` `-Out` `-Version` `-Clean` `-SkipFrontend` `-SkipWorker` `-Extras` `-Arch` | `dist\server`（`VERSION.txt` 记录 arch/worker/pgsql）（`-Extras` 加 start.bat、手册、样本） |
| `scripts\make-zip.ps1` | 最高压缩 ZIP（Python deflate 9） | `-Source` `-Zip` `-TopFolder` | zip |
| `scripts\build-desktop.ps1` | Electron 应用 + electron-builder：NSIS 安装包 + 便携 ZIP（消费服务端包），并在接受产物前校验包内 PE 架构 | `-Version` `-ServerDir` `-Out` `-Arch` `-Clean` `-SkipInstall` `-NoInstaller` `-NoZip` | `dist\desktop\<arch>` |
| `scripts\verify-windows-package.ps1` | 校验解包目录中各可执行文件的 PE machine 类型（Electron/oa-agent.exe = 目标架构，worker/PostgreSQL = x64） | `-Dir` `-Arch` | 表格，不符则退出码 1 |
| `scripts\dist-windows.ps1` | 完整 Windows 发行（**一个架构**）：版本 → 测试 → 服务端包 → 桌面版 → 服务端 zip → 校验和 | `-Arch x64\|arm64` `-Version` `-Mode` `-SkipTests` `-Clean` `-SkipBundle` `-SkipFrontend` `-SkipWorker` `-NoServerZip` | `dist\release\<版本>\` |
| `scripts\dist-linux.sh` | 调用 `deploy/linux/build-release.sh` 生成 Linux 发行包 | `--version` `--out` `--archs` | `dist/release/<版本>/` |
| `scripts/release-assets.sh` | 发布资产名契约（唯一来源，按组输出文件名） | `--version` `--group` | 文件名列表 |
| `scripts/release-check.sh` | 发布闸门：标签必须是 `v<semver>` 且与 `VERSION` 一致；输出 tag/version/prerelease | `--tag` | key=value |
| `scripts/release-assemble.sh` | 校验资产集合恰为契约、生成统一 `SHA256SUMS` | `--version` `--dir` | `SHA256SUMS` |
| `scripts/release-notes.sh` | 由 `release-notes.md.tmpl` 生成发布说明 | `--version` `--tag` `--repo` `--registry` `--prerelease` | Markdown |
| `scripts/release-publish.sh` | 用 `gh` 草稿创建/更新 → 上传 → 校验 → 发布（可重复运行） | `--tag` `--version` `--dir` `--notes` `--repo` | GitHub Release |
| `scripts/test/release.sh`、`linux-bundles.sh` | 上述脚本与 Linux 分架构安装包的离线测试（假 `gh`、假 `go`） | - | 通过/失败 |
| `scripts\build-all.ps1` | 当前系统能做的全部：Windows 发行（`-Arch x64,arm64`）+ （有 bash 时）Linux 发行 | `-Version` `-SkipTests` `-Clean` `-SkipLinux` `-Arch` | 同上 |
| `deploy\windows\build.ps1` | 旧入口：仅服务端单文件夹包（含 start.bat），内部调用 `build-server-bundle.ps1 -Extras` | `-Mode` `-Out` | `dist\oa-agent` |

调试包：`-Mode debug`（后端带 `-tags debug` 日志，便于排查）。

## 产物（`dist\release\<版本>\`，Windows 每个架构一套）
| 文件 | 内容 |
|---|---|
| `oa-agent-<版本>-windows-<arch>-setup.exe` | NSIS 安装程序：非一键，默认当前用户（可选所有用户），可改安装目录，**工作目录选择页**，桌面+开始菜单快捷方式，中文/英文界面（启动时选择语言），安装前自动关闭运行中的实例（含后台服务/数据库），卸载时默认保留 `%LOCALAPPDATA%\OA-Agent` 数据并提供“同时删除我的数据”复选框，写入版本/发布者注册表项（`Software\OA-Agent`） |
| `oa-agent-<版本>-windows-<arch>-portable.zip` | 便携桌面版（旧名 `...-windows-x64.zip`）：解压即用；含 `portable.flag` 时数据保存在程序旁 `data\`，删除该文件则用 `%LOCALAPPDATA%\OA-Agent` |
| `oa-agent-<版本>-windows-<arch>-server.zip` | 纯服务端文件夹（无 Electron）：`start.bat` 启动，浏览器访问；配置见 `oa-agent.env` |
| `SHA256SUMS-windows-<arch>.txt` | 本地构建的便利校验文件（`hash  文件名`）；**发布用的 `SHA256SUMS` 由 CI 最后统一生成** |

`<arch>` 为 `x64` 或 `arm64`。

静默安装：`setup.exe /S [/D=<安装目录>] [/ARCHIVE="D:\OA归档"] [/allusers]`（静默时不显示工作目录页，仅当给出 `/ARCHIVE=` 才预设归档目录，否则首次运行时询问）；静默卸载：`"<安装目录>\Uninstall OA-Agent-Desktop.exe" /S`（保留数据）。

## 工作目录（用户可自定义）
- **归档文件夹**：安装时（向导页或 `/ARCHIVE=`，写入 `%LOCALAPPDATA%\OA-Agent\install-preset.ini`）、首次运行（弹窗，默认 `文档\OA-Agent\归档`，便携版默认程序旁 `归档\`）、之后随时通过“桌面版设置…”窗口（迁移并逐文件校验 / 直接使用新位置，失败自动回滚）。
- **数据目录**（数据库、临时文件、日志）：首次运行“高级”折叠项、菜单“迁移数据目录…”、或环境变量 `OA_AGENT_DATA_DIR`。
- **服务端包**：首次运行 `start.bat` 会弹出文件夹选择窗口询问工作目录（`first-run.ps1`，写入 `oa-agent.env` 的 `OA_ARCHIVE_ROOT`）；**以后随时双击 `change-workdir.bat` 更改**（可把已有归档文件复制到新位置，不覆盖、不删除旧文件；也可直接编辑 `oa-agent.env`）。`OA_DATA_DIR` 同样在 `oa-agent.env` 中说明。
- 详情见 `desktop\README.md`。

## 签名与 SmartScreen
签名是**可选**的。设置环境变量后 `build-desktop.ps1`/`dist-windows.ps1` 自动签名安装程序与主程序：
```powershell
$env:CSC_LINK = "C:\path\cert.pfx"      # 或 base64 / https 地址
$env:CSC_KEY_PASSWORD = "<密码>"          # 切勿提交到仓库
```
（Azure Trusted Signing / SignTool 方案见 electron-builder 文档 `win.azureSignOptions`/`win.signtoolOptions`。）未签名的包可正常构建与运行，但 Windows SmartScreen 首次运行会提示“已保护你的电脑”，需点“更多信息 → 仍要运行”；建议对外发布时使用 EV/OV 证书。后端 `oa-agent.exe`、Worker 与 PostgreSQL 也可能被杀毒软件误报，必要时加入白名单。

## 发布流程（GitHub Release，标签驱动）

### 资产命名（契约，`scripts/release-assets.sh` 是唯一来源，版本号不带 `v`）
| 资产 | 说明 |
|---|---|
| `oa-agent-<版本>-windows-x64-setup.exe` / `-portable.zip` / `-server.zip` | Windows x64：安装版 / 便携版 / 仅服务端 |
| `oa-agent-<版本>-windows-arm64-setup.exe` / `-portable.zip` / `-server.zip` | Windows 11 on Arm：同上（**实验性**） |
| `oa-agent-<版本>-linux-amd64.tar.gz`、`oa-agent-<版本>-linux-arm64.tar.gz` | Linux 分架构安装包（与 `oa-agent-deploy` 镜像的 `/deploy` 同构，只含对应架构的 `oa-agentctl`） |
| `install.sh` | Linux 一键安装脚本 |
| `oa-agentctl-linux-amd64`、`oa-agentctl-linux-arm64` | 管理工具（静态 Go 二进制） |
| `oa-agent-source.tar.gz`、`oa-agent-source.tar.gz.sha256` | 源码 + 部署文件（`install.sh` 无镜像仓库时下载并校验） |
| `SHA256SUMS` | 以上全部资产的 SHA-256（`hash  文件名`，按名称排序，最后一个作业从下载的产物生成） |

共 14 个文件。名称是对外契约，改动需同步 `release-notes.md.tmpl`、README、本文与测试。**不提供 riscv64**：Worker 依赖（onnxruntime、opencv、PyMuPDF）没有 riscv64 轮子与基础镜像，所以没有 riscv64 镜像与完整安装包；只有纯 Go 的 `oa-agentctl` 可自行交叉编译（`GOOS=linux GOARCH=riscv64`，实验性、未测试、不支持完整栈），它不在发布清单与 `SHA256SUMS` 中，发布不依赖它。

### 版本以标签为准
`release.yml` 的 `prepare` 作业运行 `scripts/release-check.sh`：标签必须是 `v<主>.<次>.<修>[-后缀]`（如 `v1.2.0`、`v1.2.0-rc.1`，不允许 `+`），且根目录 `VERSION` 必须等于标签去掉 `v`，否则失败并提示修复办法。通过后所有作业用标签的版本号设置 `OA_VERSION`（资产名、二进制版本、`VERSION.txt` 都来自它），Docker 镜像标签（`images.yml`，标签去掉 `v`）与之相同。含 `-` 的版本自动标为预发布（不更新 latest，镜像不打 `<主>.<次>` 标签）。

### 步骤
1. 改 `VERSION`（如 `0.2.0`），更新需要的文档/更新说明，提交并推送到 `main`，等 `check.yml` 通过。
2. （建议）先**演练**：GitHub -> Actions -> `Release` -> Run workflow，保持 `dry_run` 勾选（默认）。会构建所有资产并上传为 workflow 产物（`asset-*` 与汇总的 `release-assets`，含发布说明草稿 `release-notes.md`），**不发布任何东西**。
3. 打标签并推送：`git tag v0.2.0 && git push origin v0.2.0`。
4. 工作流 `Release`（`release.yml`）与 `Container images`（`images.yml`）同时运行：
   - `prepare`：校验标签/VERSION（只读）。
   - `windows`（矩阵 `x64`、`arm64`，均在 `windows-latest` 上）：`scripts/dist-windows.ps1 -Arch <arch>`；x64 作业额外跑测试。
   - `linux`：`scripts/dist-linux.sh`（Go 交叉编译两个架构，无需 QEMU）。
   - `release`（`needs: prepare, windows, linux`，**唯一拥有 `contents: write` 的作业**，其余只读）：下载产物 -> `release-assemble.sh`（集合必须恰好等于契约，生成 `SHA256SUMS`）-> `release-notes.sh` -> `release-publish.sh`：以**草稿**创建 Release、上传全部资产（`--clobber`）、核对资产清单与数量，全部正确后才公开；任一步失败则 Release 保持草稿（用户不可见）。使用预装 `gh` 与 `GITHUB_TOKEN`，不用第三方发布 Action。
5. 在 Releases 页检查（Windows 安装、解压、校验和），必要时编辑说明。
6. 并发：同一 ref 的发布运行串行，从不取消。

### 重跑、演练、手动发布
- **重跑**：Actions 中对该标签的运行点 “Re-run all jobs”（或 Run workflow，`Use workflow from` 选该标签，取消勾选 `dry_run`）。流程幂等：已存在的 Release 先退回草稿、刷新说明、删除不属于契约的旧资产、`--clobber` 覆盖资产，再校验并重新公开。
- **演练**：`dry_run`（默认勾选）只上传 workflow 产物；`dry_run=false` 必须从标签本身启动，否则 `prepare` 报错。可选输入 `tag` 指定演练用的标签名（默认 `v<VERSION>`，仍须与 `VERSION` 一致）。
- **本地演练纯脚本部分**：`bash scripts/test/release.sh`（标签闸门、资产契约、SHA256SUMS、说明、发布流程对假 `gh`）与 `bash scripts/test/linux-bundles.sh`（Linux 分架构安装包）；工作流语法：`docker run --rm -v "<repo>:/repo" -w /repo rhysd/actionlint:latest -color`。

### 签名
签名是可选的：在仓库 Settings -> Secrets and variables -> Actions 添加 `CSC_LINK`（PFX 的 base64 或地址）与 `CSC_KEY_PASSWORD`，`windows` 作业自动签名两个架构的安装包与主程序；不添加则为未签名（说明里已写 SmartScreen 提示）。除此之外发布不需要任何密钥；发布说明里的镜像仓库地址取自变量 `ACR_REGISTRY`/`ACR_NAMESPACE`（未配置则显示占位符）。

### 回滚 / 撤回
- 资产有误：修复后对同一标签重跑（见上）。
- 撤回发布：`gh release edit v0.2.0 --draft`（立即对用户隐藏）或 `gh release delete v0.2.0 --yes`（保留标签）；彻底废弃再 `git push origin :refs/tags/v0.2.0` 并 `git tag -d v0.2.0`。已推送的镜像标签在仓库中另行处理（`oa-agentctl upgrade --tag <旧版本>` 可回退服务器）。
- 版本号不要复用：修正后用新补丁号（如 `v0.2.1`）重新发布，除非发布尚未被任何人下载。

### Windows arm64 决策表
| 组件 | x64 包 | arm64 包 | 依据 |
|---|---|---|---|
| Electron 外壳（`OA-Agent-Desktop.exe` 与其 DLL） | 原生 x64 | **原生 arm64** | electron-builder `--arm64` 在 x64 机器上即可打包，无需运行 arm64 代码 |
| 后端 `oa-agent.exe`（Go） | 原生 x64 | **原生 arm64** | `GOOS=windows GOARCH=arm64` 交叉编译，纯 Go（CGO 关闭） |
| NSIS 安装程序 | x64 包 | arm64 包（NSIS 安装程序壳本身是 x86 程序，所有 Windows 上均可运行；载荷为 arm64） | electron-builder `nsis` 支持 `arm64` |
| 文档 Worker（PyInstaller：onnxruntime、opencv、PyMuPDF、numpy、Pillow、RapidOCR） | 原生 x64 | **x64（仿真运行）** | PyPI 上 `opencv-python 5.0.0.93` 与 `PyMuPDF 2.0` **没有** `win_arm64` 轮子（onnxruntime、numpy、Pillow 有；rapidocr 为纯 Python），只能打包 x64 Worker；因此 Worker 总是在 `windows-latest`（x64）上用 x64 Python 构建（`build-worker.ps1` 会拒绝非 AMD64 的 Python） |
| 内置 PostgreSQL | 原生 x64 | **x64（仿真运行）** | zonky `embedded-postgres-binaries` 只有 `windows-amd64`/`windows-i386`，没有 `windows-arm64`；Windows 11 on Arm 可运行 x64 用户态程序 |
| 构建机器 | `windows-latest` | `windows-latest`（交叉打包） | 不需要 `windows-11-arm` 运行器：它对公共仓库免费、预装 Go 1.24/Node 24/Python 3.13（arm64），但私有仓库可用性与计费需自行确认，且 Worker 无论如何要 x64 Python；因此不依赖它，在私有仓库同样可用 |

运行时防护：`oa-agent.exe` 用原生 ARM64 进程启动 x64 的 `postgres.exe` 与 `document-worker.exe`（子进程由 Windows 仿真层承载；`desktop/src/paths.js`、`backend/internal/supervisor` 与脚本不依赖 `process.arch`，路径与文件名与 x64 相同，仅诊断信息里输出 `os.arch()`）。构建时 `scripts/verify-windows-package.ps1` 检查 PE machine 类型（Electron/`oa-agent.exe` = 目标架构，Worker/PostgreSQL = x64），不符则构建失败；`VERSION.txt` 记录 `arch=`、`worker=x64`、`pgsql=x64`。

**状态：实验性，未在真实 ARM64 硬件上测试。** 发布说明已如此标注。在 Windows 11 on Arm 上手工检查清单：
1. 安装/解压后启动：任务管理器中 `OA-Agent-Desktop.exe`、`oa-agent.exe` 为 “Arm64”，`postgres.exe`、`document-worker.exe` 为 “x64”（仿真）。
2. 首次运行向导、选择归档目录，数据库初始化成功（首次较慢）。
3. 导入 Word/Excel/PDF/图片各一份：文本抽取与 OCR 正常（OCR 在仿真下较慢，注意超时）。
4. 预览 -> 审批 -> 执行 -> 台账与 Excel 导出。
5. 退出后无残留 `postgres.exe`/`document-worker.exe`/`oa-agent.exe`；便携版数据写入程序旁 `data\`。
6. 卸载（数据保留）；静默安装 `/S`。
若 Worker/PostgreSQL 在仿真下不稳，后续可：等 PyMuPDF/opencv 发布 `win_arm64` 轮子后切换原生 Worker（在 `windows-11-arm` 运行器上构建）；PostgreSQL 需自行编译 arm64 版本。

## 体积
压缩策略：NSIS 使用 LZMA（electron-builder `compression: maximum`），ZIP 使用 deflate 9，只保留 zh-CN/en-US 语言包，裁剪 PostgreSQL 中用不到的 DLL。Worker（PyInstaller，含 OCR/PDF 库）是体积主因。实际体积见每次 `dist-windows.ps1` 末尾的汇总表。

## 测试
- 桌面版纯 Node 单测：`cd desktop && npm test`。
- 冒烟（CDP/puppeteer-core，需要 Edge）：`desktop\test\smoke.mjs`（启动画面先于主窗口出现并在界面加载后关闭、主窗口加载 127.0.0.1、数据目录位置、单实例、退出后无残留 `oa-agent`/`postgres`/`document-worker` 进程）。变量见文件头：`SMOKE_EXE`、`SMOKE_WORK`、可选 `SMOKE_PORTABLE=1`、`SMOKE_FIRSTRUN=1`。

## 容器镜像（Linux 版）与 `images.yml`
`.github/workflows/images.yml` 在**每次 push（任意分支）、`v*` 标签、PR 和手动运行**时构建三个镜像（矩阵 `api`、`worker`、`deploy`；`deploy` 即安装包镜像，Dockerfile 为 `deploy/docker/Dockerfile.deploy`），并推送到阿里云 ACR 等镜像仓库：

- 凭据只来自 GitHub Actions：Secrets `ACR_USERNAME`、`ACR_PASSWORD`；Variables（或 Secrets）`ACR_REGISTRY`、`ACR_NAMESPACE`。仓库里没有任何真实值；参考实例的公网/VPC 地址与命名空间仅作为默认值写在工作流注释和 [部署指南-Linux.md](部署指南-Linux.md) 第 11 节。
- PR 只构建、不登录、拿不到机密；没有配置机密（例如 fork）时同样只构建，作业摘要会写明“Push skipped”，工作流保持绿色。
- 平台：默认分支和 `v*` 标签 = `linux/amd64` + `linux/arm64`（api、worker、deploy 都是；推送后校验清单），其他分支与 PR 只有 `linux/amd64`；arm64 的 Worker 在 QEMU 下安装 OCR 依赖，冷缓存时很慢（20–40 分钟），有 GitHub Actions 缓存后明显更快。
- 标签：`sha-<7位>`（每次 push）、`<分支>`（分支 push）、`latest`（仅默认分支）、`<版本>` 与 `<主>.<次>`（`v*` 标签）；构建参数 `OA_VERSION`（标签去掉 v，或 `VERSION` 文件 + `+<7位提交>`）与 `OA_COMMIT`；缓存 `type=gha`（每个镜像一个 scope）；`provenance: false`、`sbom: false`；分支 push 与 PR 只构 `linux/amd64`（快）；**`v*` 标签自动构 `linux/amd64` + `linux/arm64`**（三个镜像；api、deploy 在构建机上交叉编译，worker 的 pip 安装在 QEMU 下运行，较慢但仅限标签）；手动运行可勾选 `arm64` / `arm64_worker` 在分支上试构。
- 并发：同一 ref 的新提交取消旧运行，标签运行从不被取消；权限仅 `contents: read`；第三方 Action 固定主版本（更严格可固定 SHA）。
- `scripts/push-images.sh` 是同一套规则的本地/手动版本（`--print-tags`、`--print-meta`、`--dry-run`），工作流用它生成 `OA_VERSION/OA_COMMIT` 并做标签一致性告警。用 `registry:2` 在本机 `localhost:15000/koch2333` 即可完整演练推送、安装与升级。
- 校验：`docker run --rm -v "<repo>:/repo" -w /repo rhysd/actionlint:latest -color`。

## CI 用法
```yaml
- run: powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dist-windows.ps1 -Arch arm64 -SkipTests   # check.yml 已跑测试时
```
Windows runner 需要先建立 **x64** Worker venv（见 release.yml）。Linux 任务只调用 `scripts/dist-linux.sh`。完整发布见上文“发布流程”。
